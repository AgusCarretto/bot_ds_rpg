# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Asado y Acero RPG" — a text-based RPG Discord bot (Spanish, Argentine-themed). C#/.NET 10,
Discord.Net (slash commands via `InteractionService` + legacy text commands via `CommandService`),
PostgreSQL via Dapper/Npgsql (no EF Core). Code comments and all user-facing text are in Spanish; since v0.26.0 the main screens also exist in English for players who choose it (`/language`, see "Language" at the end).

## Commands

```
dotnet build              # compile — do this after any change
dotnet run                # start the bot (needs .env or User Secrets configured, see below)
.\tests\run-all.ps1       # the 63 verification harnesses against a LOCAL database (or tests/run-all.sh); -Only name1,name2 for some
```

**Tests (since v0.18.3; `tests/`, `tools/`, design in `tests/README.md`)** — until v0.18.2 the ~40 harnesses mentioned all over this file ("Harness: `dailytest`", "`typedtest`"...) lived outside the repo, in a temporary folder of whoever was
working, and `MEJORAS.md` counted "zero tests" as a debt. Now each is a console project `tests/<name>/<name>.csproj` + `Program.cs` that references the real bot project (no Discord) and prints `[OK]`/`[FALLA]` per check, ending with `TODO OK`
(exit 0) or `N FALLAS` (exit 1); they are deliberately plain scripts, not a test framework. `tests/Directory.Build.props` holds everything the csprojs share, `tests/Shared/TestEnv.cs` the connection string (the `Postgres__ConnectionString`
variable, or the `.env` of the repo root, or — in a git worktree — the main folder's) and `RepoRoot`; **never write an absolute path in a harness**. **They write and delete data** (disposable users `999000000000xxxxx`, and a few touch the
catalog or `cooldowns` for a moment), so `TestEnv` **refuses a non-local database** unless `HARNESS_ALLOW_REMOTE=1`: never point them at production. The main csproj excludes `tests/**` and `tools/**` from its own compilation (`Compile
Remove`) and `.dockerignore` keeps them out of the image. **`dotnet build` plus `.\tests\run-all.ps1` is the mechanical check now**; when a change breaks a harness, first decide whether the harness encoded the OLD behaviour on purpose (update it, like the
XP ranges in `stage11test`) or the code is wrong. `tools/balance2` is the calibration simulator (the real `CombatTurnResolver` and the local monsters): parts A–J, e.g. `dotnet run --project tools/balance2 -- J` measures every boss against
the previous zone's gear.

### Database setup (fresh machine)

`Database/schema.sql` is self-sufficient for a brand-new database (creates every table/column/
extension currently in use). Run in this exact order against an empty database:

```
schema.sql → seed.sql → add_weapon_family.sql → seed_class_gear_and_monster_drops.sql
  → seed_consumables_and_base_swords.sql → seed_zones_and_monsters.sql → seed_zone_bosses.sql
  → seed_travel_monsters.sql → finalize_monster_roster.sql
  → seed_recipes.sql → seed_zone2_gear_and_recipes.sql → seed_zone3_gear_and_recipes.sql
  → seed_zone4_gear_and_recipes.sql → seed_zone5_gear_and_recipes.sql
  → finalize_consumable_catalog.sql → remove_legacy_consumables.sql → rebalance_consumable_prices.sql
  → rework_food_catalog.sql → seed_boxes.sql → rework_drops_and_recipes.sql → rework_boxes.sql
  → update_item_emojis.sql → update_monster_portraits.sql → seed_pets.sql → seed_fogon.sql
  → seed_zone_boxes.sql → retire_box_trophies.sql → rebalance_dust.sql → update_item_emojis.sql (again)
```

**The emoji script runs TWICE on purpose**: `update_item_emojis.sql` sits at position 21, but `seed_pets.sql`, `seed_fogon.sql` and `seed_zone_boxes.sql` create items AFTER it, so its UPDATEs-by-name found nothing for the Trinche, the Brasa, the eggs and the two new boxes and a fresh install ended with them empty (found on 2026-10-09 when the Fogón pair got its art). The last line of `run_fresh_install.sql` runs it again, and the scratch-vs-live comparison of `name=emoji` for every item came out identical. Any item created late in the order gets its emoji in `update_item_emojis.sql` and nothing else.

`seed_recipes.sql` must come after every seed that creates items it uses: a recipe whose result or ingredient
item doesn't exist yet would be silently skipped (or created *without* that ingredient), so the seed verifies
itself and raises instead. (`seed_zone_bosses.sql` used to be missing from this list, so a fresh install had no
zone bosses at all.)

`Database/run_fresh_install.sql` runs all twenty-eight in this exact order (plus the emoji script once more at the end) in one shot via `psql` (or
pgAdmin's "PSQL Tool", NOT its plain Query Tool — both need real `psql`, since it uses the `\ir`
meta-command) — **only against a genuinely empty database**, never against one with existing data
(see below, several of these are not safe to re-run).

The other `Database/add_*.sql` / `cleanup_*.sql` / `fix_*.sql` files are historical incremental
migrations for databases that predate `schema.sql` catching up to include everything inline —
**do not run them against a fresh install**, `schema.sql` already has their end state. They matter
only if you're patching an old, already-running database that hasn't been recreated from scratch.

`seed.sql`, `add_weapon_family.sql`, and `seed_class_gear_and_monster_drops.sql` insert
unconditionally and will duplicate rows if run twice against a database that already has their
data (their own header comments predate `items.name UNIQUE`, so they undersell it — with that
constraint now in schema.sql, their `ON CONFLICT DO NOTHING` inserts are actually idempotent too,
but don't rely on that for the `UPDATE`/data-shape parts). Everything else in the order above
(`seed_consumables_and_base_swords.sql`, `seed_zones_and_monsters.sql`, `seed_zone_bosses.sql`,
`seed_travel_monsters.sql`, `finalize_monster_roster.sql`, `seed_recipes.sql`, `seed_zoneN_gear_and_recipes.sql` (N = 2..5), `finalize_consumable_catalog.sql`, `remove_legacy_consumables.sql`, `rebalance_consumable_prices.sql`, `rework_food_catalog.sql`, `seed_boxes.sql`, `rework_drops_and_recipes.sql`, `rework_boxes.sql`, `update_item_emojis.sql`, `update_monster_portraits.sql`, `seed_pets.sql`, `seed_fogon.sql`, `seed_zone_boxes.sql` — **the last one must be applied through `add_zone_boxes.sql` to a live database BEFORE the v0.14.0 binary**: the code reads the `zone_boxes` table in every mission/achievement payout and boss repeat) is
safe to re-run (**`rework_boxes.sql` must be applied to a live database BEFORE starting the v0.8.0 binary**: the code reads the `boxes.min_items/max_items` columns it adds; the same goes for **`update_monster_portraits.sql` before the v0.8.2 binary**, which reads `monsters.portrait_emoji`, and for **`add_pets.sql` before the v0.10.0 binary** — it creates the `pet_species`/`player_pets` tables, runs `seed_pets.sql` and hands an egg to every player who had already beaten a zone boss; re-runnable, and the code reads those tables on every fight start), **with one exception since v0.7.0**: `rework_drops_and_recipes.sql` supersedes the drops, the boss drops, the Zone-1 roster and every recipe of the seeds before it
(`finalize_monster_roster.sql`, `seed_zone_bosses.sql`, `seed_travel_monsters.sql`'s boss/roster parts, `seed_recipes.sql`, `seed_zoneN_gear_and_recipes.sql`). Never re-run those alone on a live database: they would bring the old state back (or fail on
items that no longer exist). The rework script always goes after them and is itself re-runnable — but it deletes on purpose (retired items vanish from inventories with no refund; it prints a NOTICE with what was lost), so take a `pg_dump` first.

**Known recurring problem**: catalog items have repeatedly been added by hand directly to a
Postgres instance on one machine and never captured in a script, so a fresh install on another
machine silently ends up missing items (this happened at least twice — weapons and the entire
Consumable catalog; and a third time with Carbón, hand-edited from Común to Raro on the live DB while the seed kept
creating it Común, which on a fresh install would have doubled Hierro's `/mine` rate and unbalanced the recipes). If you
add/edit `items` rows by hand, write the INSERT into a new `Database/*.sql` file in the same session, or the next fresh
install will be short again. **Way to check, and worth doing after any catalog change**: create a scratch database, run
`run_fresh_install.sql` against it, and diff a few `concat_ws(...)` summary queries (items, recipes, monsters, boxes, buffs)
between it and the live one — they must be identical (that comparison is how the Carbón drift was found).

## Architecture

**Layering**: `Modules/` (Discord command handlers) → `Repositories/` (Dapper + SQL, one per
aggregate: `IUserRepository`, `IItemRepository`, `IInventoryRepository`, `IShopRepository`,
`ICraftingRepository`, `IRecipeRepository`, `ICasinoRepository`, `IAdventureRepository`,
`IGatheringRepository`, `ICooldownRepository`, `IProgressionRepository`, `IGameEventRepository`, `ITransferRepository`,
`IBoxRepository`, `IBuffRepository`, `IMissionRepository`, `IAchievementRepository`, `IBankRepository`, `IDustRepository`, `IPetRepository`, `IBlessingRepository`, `IFuegoNuevoRepository`, `IReminderRepository`, `IVoteRepository`) + `Services/` (stateful
or pure-logic helpers that don't touch SQL directly) + `GameData/` (pure calculators/catalogs, no
I/O — `LevelingCalculator`, `RarityCatalog`, `CombatMath`, `ClassPassives`, etc.). There is no
"DatabaseService" god-object — each repository owns its own slice of the schema.

**Dual command surface**: every player-facing feature is exposed twice — as a slash command
(`Modules/*Module.cs`, `InteractionModuleBase<SocketInteractionContext>`) and as a text command
with prefix `"aa "` (`Modules/TextCommandModule*.cs`, partial class split by domain, `ModuleBase
<SocketCommandContext>`). The text-command side never reimplements logic: it calls the exact same
static `Execute*Async` methods and public `Build*Embed` methods that the slash module exposes, so
behavior and embeds stay identical. When adding a new player-facing command, follow this pattern:
put the real logic in a `public static` method on the slash module (parameterized, no `Context`
dependency) and have both the slash handler and the `TextCommandModule` partial call it.

**Transactions**: every operation touching gold, inventory, or cooldowns opens its own
`DbConnection`/`DbTransaction` explicitly (not `IDbConnection` — see `Data/IDbConnectionFactory.cs`)
and either commits once at the end or rolls back on any failure/precondition-not-met. Two recurring
patterns, both in `Repositories/TransactionalHelpers.cs`:
- **Guarded update**: `UPDATE ... WHERE <precondition still holds> RETURNING ...` — if the
  precondition (enough gold, enough items, cooldown expired) fails, zero rows come back and no
  read-then-write race is possible. Used for cooldown claims (`CooldownGuard`), gold spends, item
  decrements.
- **`SELECT ... FOR UPDATE`** — used when the update needs a computed value from the current row
  first (leveling curve, HP delta), e.g. `LevelingApplier.ApplyAsync`.

Never add a check-then-act sequence across two separate statements without one of these guards —
that's exactly the double-click/concurrent-execution bug class this schema is designed to prevent.

**Item catalog is data-driven, not code-driven**: `items.type` (`Weapon`, `Amulet`, `Consumable`,
`Madera`, `Mineral`, `Material`) and `items.weapon_family` (`Espadas`/`Dagas`/`Arcos`/`Grimorios`,
matching `ClassCatalog.WeaponType`) drive gameplay — `/chop` and `/mine` only ever drop their own
type, `/hunt`/`/travel` drops are `type = 'Material'` exclusively (never Madera/Mineral, never
Weapon/Amulet), `/shop` only lists/sells `type = 'Consumable'`, a class weapon's ATQ is a FIXED number (since v0.27.0 there is no class-synergy multiplier: `weapon_family` and `class_requirement` only decide which class forges and sees the recipe). Forge recipes also live in the
database (`recipes` + `recipe_ingredients`, referencing `items` by id), not in code — there used to
be a `GameData/CraftingCatalog.cs`, it was deleted in favor of `Repositories/RecipeRepository.cs`.

**Zones**: the world is split into difficulty-scaled zones (`zones` table, `Repositories/IZoneRepository.cs`).
Zone IDs are shown to players ("Zona 2"), so they should be consecutive 1..N in difficulty order; a failed
insert burns identity numbers and leaves gaps — `Database/renumber_zones_consecutively.sql` fixes an existing DB
(it rewrites every column that stores a zone id, so any *new* column holding a zone id must be added to it).
Each player has `users.current_zone_id` (default 1); `/zona [id]` moves them after validating
`zones.min_level`, `/zonas` lists them. `/hunt`, `/travel` and `/boss` are all zone-scoped, and every
monster lives in the DB (`monsters` + `monster_drops`, `Repositories/IMonsterRepository.cs`; nothing is
hardcoded in `MonsterCatalog` anymore). A zone has three *mutually exclusive* kinds of monster
(`monsters.is_boss` / `monsters.is_travel`, `CHECK (NOT (is_boss AND is_travel))`): the `/hunt` pool
(`PrepareHuntAsync`, **2 in every zone**), the boss (`/boss`, alone or with friends) and **one dedicated
`/travel` monster per zone** (`PrepareTravelAsync`, `Database/seed_travel_monsters.sql`). The travel monster
is the average of that zone's commons at HP ×1.25 / damage ×1.1 (an élite, not a boss — measured with the
real `CombatTurnResolver`, see the seed header), and `CombatRewardCalculator.RollTravelReward` pays the
**whole `/hunt` formula ×30** (`TravelRewardMultiplier` — what the 30-minute cooldown is worth in hunts; it was ×10 with a 10-minute cooldown until v0.7.1, so the payout per minute is unchanged). So
travel rewards follow the zone ladder automatically: a new zone's travel payout is set by the
`gold_reward`/`xp_reward` bonus of its monster, same as hunts. If you add a zone, add its travel monster or
`/travel` answers "zona sin monstruos" (without charging the cooldown). **A boss pays more than a travel**: `RollBossReward` is the `/hunt` formula (plus the boss's own big gold/XP bonus,
`seed_zone_bosses.sql`) ×15 (`BossRewardMultiplier`), i.e. 2.0–4.7× a travel of its zone (zone 1 the most; measured in the stage-11 harness at the zone's level). History: ×1 until v0.6.0 (it paid HALF a travel), ×6 for a 30-minute cooldown, and ×15 since v0.8.0
for a ONE-HOUR cooldown (parity per minute against the 30-minute travel would be ×12, the extra 25% was the owner's "un poco más"). Since v0.8.1 the boss cooldown is **5 hours** again (too many boss chests at 1 hour) and the owner asked NOT to touch rewards, so the ×15 stays and the boss now pays well under a travel per minute of cooldown — if it should feel worth the wait, raise this one constant; every raid participant gets the full amount. It speeds up
leveling (a player cycling hunt + travel + boss on cooldown levels faster than with ×1), so if pacing needs to slow down, lower this one constant. **The boss no longer drops a material: its single `monster_drops` row is the zone's CHEST** (`Cajón de Pino` Z1, `Baúl de Roble` Z2, `Arcón de Hierro` Z3, `Cofre de Oro` Z4, **`Cofre de Escoria` Z5 since v0.14.0**, and `Brasero del Fogón` for the Asador), 100%
the first time THAT player beats it **in this lap** (`BossChest.IsFirstClear`: `highest_zone_cleared` for the ladder, `gate_cleared` for the Fogón — both read before applying the victory, solo and per participant in a raid; both reset with each Fuego Nuevo) and, **since v0.14.0, repeats pay the smaller box of the zone's `zone_boxes` row with role `repeat` and ITS chance** (Z1 Pino 100 %, Z2 Pino, Z3 Roble, Z4 Arcón de Hierro 60 %, Z5 Arcón, Fogón Arcón; it used to be "40 % of the big chest" for every zone, which made the Cofre de Oro the most profitable thing in the game).
The chance comes from the database (`BossChest.RepeatAsync`, `CombatRewardCalculator.BossChestChancePercent(firstClear, repeatChancePercent)`; there is no `BossChestRepeatPercent` constant any more) and `/drops` prints the same row. The chest and the repeat box travel the
normal drop path (`ApplyBossVictoryAsync`) and are opened with `/open`; the Arca del Soberano stays achievement-only.

**Free boxes per zone: the `zone_boxes` table (v0.14.0, "cofres parejos"; `GameData/ZoneBoxes.cs`, `Repositories/ZoneBoxQueries.cs`, `Services/ZoneBoxService.cs`, `Database/seed_zone_boxes.sql` + `add_zone_boxes.sql`, design: `docs/superpowers/specs/2026-10-07-cofres-parejos-design.md`)** — `zone_boxes(zone_id, role, box_item_id, chance_percent)` is the ONE place that says which free box a zone gives and when: roles `repeat` (a repeated boss win, with its chance), `daily` / `weekly` (completing all the missions of the day / week), `prize` (achievement tier II and the Arena champion) and `prize_top` (tier III). It replaced the box ladder that was hard-coded in `MissionRewards`, so a new zone needs rows, not code. `BoxGrant` (ZoneTier→prize, ZoneTierPlusOne→prize_top, Daily, Weekly) still says WHICH role a reward pays; `ZoneBoxTable` (pure) resolves it by the zone's rank and clamps an out-of-range rank (a missing role for a zone is an error and the payout throws: nothing is paid without its box). `RewardPayer` reads the table INSIDE the reward transaction; everything else goes through the 5-minute-cached `IZoneBoxService`, and the startup logs what is missing (`EnsureDatabaseAsync`). **The Cofre de Oro was cut from the free supply of the low zones** (it now shows up only from Zone 3's `prize_top`), because a free Cofre de Oro (~211k "farming minutes") outweighed several 2-hour sessions of play (measured by `Database/report_box_economy.sql`: Pino ~0.75k, Roble ~8.2k, Arcón ~43k, Cofre ~211k; a perfect 2 h session pays 3.4k / 13.9k / 28.3k / 51.6k / 90k of gold in Zones 1–5). `Database/report_economy.sql` prints the table and how many sessions a week of free boxes is worth per zone (3.5–9.9 in v0.14.0: still uneven between zones, Zone 4 being the most generous; it is data, tune it with an `UPDATE` on `zone_boxes`, no redeploy needed beyond the 5-minute cache). **Two new prize-only boxes** (not bought, not resold, `buy_price = 0`): **Cofre de Escoria** (Zone 5 boss chest, 35–65 items, Mythic rarity, gold bonus 3 % × 20–60k; its loot weights are in `seed_zone_boxes.sql`) and **Brasero del Fogón** (the Asador's chest, 25–45 items, 65 % of the draws are pet food, 40–80k gold ALWAYS: the Fuego Nuevo wipes materials, boxes and XP, so the Zone-0 prize has to be what stays — gold, pet food, pets). The Mythic fixed materials (Corteza / Meteorito) are still only in the Arca (`seed_zone_boxes.sql` verifies it).

**The /travel stopped dropping a material (v0.36.0; `Database/remove_travel_drops.sql` — run it on a live database BEFORE the v0.36.0 binary: the code reads the `travel` role of `zone_boxes` on every won /travel and the script deletes the 5 travel-drop items; `Services/TravelBox.cs`, `ZoneBoxRole.Travel`, `CombatRewardCalculator.TravelBoxChance` / `RollTravelReward(..., boxChancePercent)`, `CombatState.TravelZoneId`, harness `v0360test`)** — the owner (2026-10-28), thinking about "too many items in the inventory and too many ingredients per recipe" compared with EPIC: "¿y si sacamos el drop solo del travel y que el travel sea esa suma de xp y gold con probabilidad de sacar una caja de la zona?" and, on my proposal of bigger hunt-drop quantities, "sumale algún drop a cada uno". **Now**: a travel pays the whole hunt formula ×30 (gold and XP, unchanged) plus a CHANCE of the zone's small box, a new `zone_boxes` role `travel`: **20 % in every zone** (Z1 and Z2 Cajón de Pino, Z3 Baúl de Roble, Z4 and Z5 Arcón de Hierro: the zone's repeat box; my first proposal was 8 / 15 / 6 / 2 / 3 % — about 10-15 % of the travel's gold in farming-minute value — and the owner found it too little: «ponele 20 % a cada zona. olvidate»). One box every ~5 travels weighs a lot in Z4-Z5, where the box is an Arcón (~43k gold-equivalent): by my estimate (4 travels per perfect 2 h × 20 % × the box's value) it adds about +40-65 % on top of the gold of such a session there and +4-25 % in Zones 1-3; if it turns out too much, lower those rows with an `UPDATE` (5-minute cache; `ZoneBoxRole.All` and `Missing()` now ask for six roles per normal zone, the gate only the repeat). The chance is multiplied by `PlayerBonuses.TravelDropMultiplier` (Fuego Nuevo, pets, the Brasa Vieja blessing and the dragon's drop perk now act on the BOX chance; their texts say "caja") and capped at 100. `CombatState.TravelZoneId` (set by the starter at the start of a travel) says which zone's row to read; a travel started before the binary changed carries none and just pays no box; `TravelBox.ChanceAsync` never throws (a failure means no box, logged) and the victory shows "🎁 ¡Cayó una caja!" (`/open` it). **Data**: the 5 travel monsters stay but drop nothing; the 5 items (Cuero Grueso, Ceniza Bendita, Escoria Metálica Densa, Aliento de Fuego Eterno, Ceniza del Abismo) are deleted — whoever held some got **1 of EACH hunt drop of that zone per unit** (two ~33-minute units for one ~75-minute unit); the 25 class-weapon and amulet recipes of Zones 1-5 lost their travel ingredient (**4 → 3 types of ingredient**, the owner's complaint about recipes) and ask for more HUNT drops so the time stays about the same: Z2-5 amulets ×4 → ×7 of EACH of the two hunt drops, the Z1 amulet ×4 → ×5 (Z1 weapons just lose the leather: gathering gates them at 95-100 min); **the Z2-5 class weapons stay at ×4 of their route's drop** (`remove_travel_drops.sql` raised them to ×5 and the owner, the same day, asked «baja 1 todas las armas del tema drop»: `Database/rebalance_weapon_drops.sql`, a data-only script that a live database which already ran the first one runs on its own, and that `run_fresh_install.sql` runs right after it; production ran it on 2026-10-28 after the v0.36.0 release). Measured with `report_recipe_pacing.sql` (the model: 0.03 per minute per hunt drop): weapons ~133 min of drops, and the gathering of 6 Hierro floors them at 143 (so a weapon takes 143 min, like the 150 it took with the travel drop), amulets ~233 (were 225), Z1 amulet 167 (was 150). The Fogón gear (5 of the 10 hunt drops ×5 per piece) was not touched. The 10 remaining drops are 2 per zone, and the 3→1 exchange keeps working between each pair. Dust: the 38-per-unit travel value is gone (`Dismantling.TravelDropDust` removed). Box loot pools derive from the monsters' drops, so every box lost the travel drop (weight 2) and is worth ~7-8 % less in farming minutes (`report_box_economy.sql`, price over value: Pino 298 → 320 %, Roble 165 → 179, Arcón 94 → 102, Cofre de Oro 55 → 60); prices were not touched. `/drops` prints, for the travel block, "N% de caja" and the box instead of a drop. The migration is re-runnable (no travel drops = nothing to do) and sits after `add_dragon_food.sql` in `run_fresh_install.sql`; the scratch fresh install matched the live catalog row for row. **Everything below about the travel drop (the ~75 min per unit "binding resource", `TravelDropChancePercent` 40 %, dust 38, 15 drops, "ONE travel unit off each class weapon") describes the game up to v0.35.0.** Do NOT re-run `rework_drops_and_recipes.sql`, `rebalance_dust.sql` or `rebalance_crafting.sql` alone on a live database after this: they bring the travel drops back or fail because they no longer exist. `tools/balance2` still simulates travel drops (its `Cfg.Travel` is 0 now). Not decided yet: one drop per zone instead of two (it would lose the physical/arcane class route).

**Drops: every monster drops exactly ONE item, and the chances are deliberately low.** Per zone there are **3 drop materials** — one per `/hunt` monster (the two "a granel": the *physical* one that Guerrero and Ninja need and the *arcane*
one for Arquero and Hechicero) and one from the travel monster ("escaso", needed by every class weapon and by the amulet) — plus the boss's chest. 20 monsters in total (2 hunt + travel + boss in each of the 5 zones, `Perro Cimarrón` was
removed). `Database/rework_drops_and_recipes.sql` (v0.7.0) is the single source of truth for the roster, the boss chests and the recipes: it verifies the final state (exactly 2 hunt + 1 travel + 1 boss per zone, one drop each — a Material for
hunt/travel, a Caja for the boss). The chances live in `CombatRewardCalculator` and nowhere else: `HuntDropChancePercent` 6 (it was 10 until v0.6.0: lowered so that reaching a zone's level is not enough to breeze through it — you have to stay and farm the gear),
`TravelDropChancePercent` **40 since v0.10.2** (the owner: "60 es una banda"; it was 60 — with the 30-minute cooldown that was 0.02 drops per minute, the same as the old 20% per 10 minutes, which is what the recipes were calibrated against — so the recipe quantities were NOT retuned on purpose: the travel drops, the "escasos" of every class weapon and amulet, now come 1.5× slower and the 5-zone class-weapon + amulet path goes from ~41 h to ~52 h of perfect play, `report_recipe_pacing.sql`; the box economy barely moves, `report_box_economy.sql` Cofre de Oro 60 % → 57 % of its price) and the boss chest chances (the boss has its own constants on purpose: it used to share the hunt formula, so lowering hunt would have silently changed it). `/drops` (`aa drops`,
`Modules/DropsModule.cs` + the pure `GameData/DropsCatalog.cs`) lists every zone's monsters and drops from those same
constants, so the list can't drift. These are **run-1 baseline values** — the reset unlocked after Zone 5 is meant to
raise drop % and material quantity. **Recipe quantities are calibrated against these chances**, so changing a chance,
a monster or a drop means re-running `Database/report_recipe_pacing.sql` (minutes of farming per recipe; pass the
chances as `-v ph= -v pt=`; `pb` no longer matters) and retuning the recipes in the rework script. Note the trap this avoids: with one item per monster each
specific item drops *more* often than with two, so lowering the percentages alone would have made progress faster,
not slower. **Co-op zone bosses — the ENGINE (`RaidModule`; until v0.18.x it was the `/raid` command)**: `Modules/RaidModule.cs` + `Services/RaidSessionService.cs`. Same
in-memory philosophy as solo combat, but a *different concurrency model on purpose*: solo combat's
`ICombatSessionService.TryAdvance` is a compare-and-swap that **rejects** the loser of a race — right
for one player double-clicking, wrong for a raid where several different players clicking "Atacar" at
once is the normal case. So a `RaidSession` is mutable and every mutation happens under
`RaidSession.Lock` (plain `lock`, so **no `await` inside it** — do the I/O after releasing).
Rules that must keep holding: (1) the phase flips to `Resolved`/`Activating` *inside the same lock*
that decides the outcome — doing it afterwards let a concurrent click trigger a second victory and
double rewards; (2) HP is persisted exactly once per participant (on flee, or at raid resolution),
never incrementally, or the delta gets applied twice; (3) fleeing forfeits the reward, like solo;
(4) `IRaidSessionService`'s player→raid index and `RaidSession.Participants` must never disagree: the
starter is added to `Participants` in `BuildSessionAsync` (they used to be registered in the index but
not the roster, so they couldn't join, couldn't start, and stayed locked out of `/hunt` after the
lobby expired), `Remove` releases players *by the index* (not by iterating `Participants`), and
`TryActivateAsync` closes the raid if it throws midway. (The old "Known gap: an `Active` raid has no
inactivity timeout" is closed since v0.19.0: the turn clock above retires whoever does not play.) Raid difficulty is not the stored boss stats: the raid boss is
`GameData/RaidDifficulty.cs` (HP +50% per extra player, plus per-zone multipliers) applied *at activation*
once the roster is final (`RaidSession.BossBaseHp` keeps the unscaled roll), so the lobby's provisional
`BossMaxHp` is meaningless until the phase flips to `Active`. The multipliers depend on the zone's **rank by
difficulty** (`RaidSession.ZoneRank`): zone 1 keeps ×2.2 HP / ×1.35 damage (calibrated on its softer boss), zone 2+
uses ×1.5 / ×1.1 because those bosses are already tuned to the zone ladder — stacking the zone-1 multipliers on a
ladder boss made the raid impossible (0-3% win). **Fight XP ×0.5 (v0.18.1; `CombatRewardCalculator.FightXpScale`; NO migration, no data change)** — the owner: "el boss de la zona 3 para pasar a la 4 está muy fácil con el equipo de zona 2… capaz subirle la vida o el daño"; then, on seeing the numbers, "puede ser que se suba de nivel muy rápido" → "0,33 es una banda, dejémoslo en 0,5". Result with the same model: level **13 / 22 / 33 / 43 at 6 / 12 / 20 / 31 h** (0.33 would be 9 / 15 / 25 / 34). Gold, drops and the boss chest do not move; missions, achievements, `/daily` and the Arena prize pay their own XP unscaled (so they weigh relatively more now); nobody loses a level (the stored level and XP stay; only new XP is slower). Not built (offered): boss stats that scale with the player's level above the zone's minimum (the real lever for a level-60 player, but it changes every boss and raid). **Zone difficulty is a ladder, and it is calibrated, not guessed.** All 5 zones are loaded. Each zone needs a *jump*
in gear, ×1.6 the previous one (class weapon ATQ per zone: Z1 +14, Z2 +30, Z3 +48, Z4 +75, Z5 +120 — the old base 9/20/32/50/80 × 1.5, baked into the number in v0.27.0 when the class-synergy multiplier was removed (`rebalance` details: `Database/remove_synergy_and_general_weapons.sql`); the single amulet's DEF is **10/35/60/85/120 since v0.15.1** (it was 10/18/30/46/75, the "low" amulets the ladder was calibrated with — see "Amulets and defense" below) — all in `rework_drops_and_recipes.sql`), and its monsters are
tuned so that **entering** with the previous zone's gear costs (~5 turns, ~47% of HP in a common fight), the zone's
own gear leaves commons at 13-18% HP (comfortable, never a walkover), and the **boss** is the exam (67-87% defeat
with the previous zone's gear, ~16% with its own). Numbers come from a simulation that drives the real
`CombatTurnResolver`: fix a nominal, strictly increasing gear ladder, then bisect the monsters' HP and damage factors
until the entry fight hits those targets (the simulator is `tools/balance2` since v0.18.3; the ladder-solving bisection was a one-off script that is NOT in the repo — rebuild it; the sensitivity to
remember is that the "exit" target controls how fast the ladder inflates, because each zone is entered with the
previous zone's exit gear). Never retune a zone's monsters without its gear (recipes) shipping with it, or it becomes
a wall, and re-measure that zone's raid when its boss changes. The whole ladder is the **run-1 baseline**: a future
post-Zone-5 reset will raise drop % and material quantities, so don't lower recipes for run 1 because they're slow.
Recipes (stats, gold, ingredients) are owned by `rework_drops_and_recipes.sql`, which deletes the old ingredients of the 30 recipes before loading, so a changed recipe never keeps stale rows.

**Combat is stateful and in-memory, not per-command**: `/hunt` and `/travel` start a turn-based

**Game events & stats (`game_events`, `player_stats`)** — ONE pipeline for "something happened": `IGameEvents.RecordAsync(discordId,

**Missions & achievements (`/missions`, `/achievements`)** — *progress is never stored*: a mission's progress is `SUM(game_events.amount)` of its
kind since the period started, and an achievement is "the `player_stats` counter reached N", so the event pipeline stays the single
source of truth and there is no assignment/progress row that can drift. The DB holds only what was **claimed** (`mission_claims`,
`achievement_claims`) plus `player_collection` (distinct "trophies" — materials no monster drops, i.e. the ones only boxes give; **there are none since v0.14.4**, see "Box trophies retired" below; it
fed the `trophy_found` counter of the Coleccionista achievement, which was removed with them; the mechanism in `BoxRepository`/`BoxModule` is dormant, kept in case they come back somewhere else).
Which missions apply is a pure function of the period start (`GameData/MissionCatalog.ForPeriod`, seeded SplitMix64 — identical for
everyone and across .NET versions; don't swap in `System.Random`, its seeded sequence is not guaranteed stable): 3 daily + 2 weekly,
never two of the same event kind, and every pool entry must be doable by *any* player (so no boss missions — level-gated — and no
fixed gold amounts — worth different per zone). Periods reset at **Uruguay midnight** (`GameData/UruguayCalendar.cs`; a fixed UTC−3
offset on purpose: Uruguay has no DST since 2015 and this avoids the OS time-zone database, whose ids differ between Windows and
Linux/Docker; weeks start Monday 00:00). Claiming (`MissionRepository`, `AchievementRepository`) is ONE transaction: lock the user row
`FOR UPDATE`, re-check the goal against the DB (a stale button can't claim an unfinished mission), `INSERT ... ON CONFLICT DO NOTHING
RETURNING` the claim mark (concurrent claims pay once — tested with 20 parallel), then `RewardPayer` pays gold + XP (with level-up) +
box in the same transaction; a reward that names a box that doesn't exist throws and rolls everything back instead of marking it
paid. Rewards are `RewardSpec` units that scale with the claimer's zone rank (`GameData/MissionRewards.cs`: gold = N × the gold of one
hunt in that zone — 14/58/118/215/375, the same unit the box prices use; XP = a % of the current level's requirement; boxes come from the `zone_boxes` table (v0.14.0)
zone ladder). Boxes are bought **one per purchase and one purchase every 2 hours** (it was 1 hour until v0.8.0; `CooldownCatalog.BoxBuy` in `/cd`, `ShopCatalog.BoxesPerPurchase`;
`ShopRepository.BuyItemWithCooldownAsync` claims the cooldown, spends the gold and adds the box in ONE transaction, so a purchase that
fails for lack of gold never burns the cooldown); food has no limit. Cooldown times are shown with days/hours/minutes
(`GameData/TimeFormat.Remaining`, the one formatter for every cooldown message). The Mythic box (Arca del Soberano) is paid only by the tier-III achievement Matajefes (Coleccionista, the other one, went away with the trophies in v0.14.4) — it holds the
very-long-term goals and must stay unbuyable. Achievements count from the day event tracking went live (v0.6), not before. The
"¡Misión completada!" / "¡Logro desbloqueado!" notices come from `Services/ProgressNotifier.cs`, called by `GameEventService` right
after each saved event: it compares the counter before and after the event, so it fires exactly when a goal is crossed and stores
nothing. Two gotchas that bit this feature: Postgres `SUM(bigint)` is `numeric` and Dapper won't read it as `long` (cast `::bigint`),
and a reward's gold/XP/box are resolved from the claimer's zone and level *at claim time*, so unclaimed achievements pay more if you
wait for a later zone (accepted).

**Player trading (`/trade`, `aa trade @user "give" "get"`)** — a 1-for-1 swap of gathering materials between two players, and nothing else:

**Blackjack (v0.25.0; `/play game:blackjack`, `aa bj <bet>` (aliases `blackjack`, `21`), `aa play blackjack <bet>`; `GameData/Blackjack.cs`, `Services/BlackjackService.cs`, `Modules/BlackjackModule.cs` + `TextCommandModule.Blackjack.cs`; NO migration; harness `v0250test`, ~56 checks)** — the owner (2026-10-22): "armate el bj entonces, aa bj 10k por ejemplo". **Rules (all in `Blackjack`, pure; the cards come from a `Func<Card>` so tests script the deck)**: infinite deck (each rank uniform in 1..13, so 4 of 13 are worth 10); two cards each; a natural (A + a ten-value) pays **3 to 2** (rounded down), both naturals push, a natural for the dealer ONLY ends the hand at once (the dealer peeks); hit / stand / **double** (only on the first two cards: one more card, the stake doubles, then it stands); reaching 21 by hitting stands by itself; the dealer draws to 17 and **stands on every 17, soft ones too**; no split, no insurance, no surrender; a win pays 1 to 1, a push returns the stake. **Measured**: with basic strategy for these rules the player gets back **0.989** per unit staked over 1,000,000 hands (house edge ≈ 1.1 %), and playing badly (stand from 12) 0.92 — below 1 like the slots; keep it below 1 if the rules are touched. **Money** (`BlackjackService`): the bet is CHARGED when the hand is dealt (`ICasinoRepository.PlaceBetAsync(id, bet, 0)`: no gold, no hand) and the payout is credited at the end (`PlaceBetAsync(id, 0, payout)`, retried up to 3 times because it is gold the player already won); doubling charges a second stake at that moment and is refused without the gold (the hand goes on). One hand per player, kept in memory (`MaxBet` 250,000,000 so a doubled win fits an int); the same concurrency model as the team boss: the hand mutates under its lock with no `await` inside, a `Busy` flag rejects other actions while the double is being charged, 6 simultaneous "aa bj 1000" deal ONE hand and charge once, 10 simultaneous "Stand" clicks pay once. **An abandoned hand does not lose the bet**: after `IdleSeconds` (90) without playing the dealer stands for the player and the result is paid; an old button then shows how that hand ended (`_finished`, 15 minutes). A bot restart does drop hands in play (same as fights): the charged bet is lost. **The admin command: `aa admingive` (v0.34.0; `Modules/AdminGiveHandler.cs`, `Modules/TextCommandModule.Admin.cs`, `GameData/AdminGive.cs`, `Services/AdminAccess.cs`, `Repositories/AdminRepository.cs`; NO migration; harness `admintest`)** — the owner (2026-10-28): "necesito poder dar cosas para probar, plata sin tenerla, cajas, items… y para sorteos, giveaways de cajas u oro… un comando solo para mí que es el admin, distinto a give, así no se pierde nada del juego". It CREATES things (it does not move them like `/give`), so it is built defensively: **(1) who**: ONLY the Discord ids in the environment variable `Admin__UserIds` (comma separated; `AdminAccess`, read from `IConfiguration["Admin:UserIds"]`); no id is written in the code or the repo, and without the variable there are no admins and the command is off. Anyone else gets NO answer at all (it does not even confirm the command exists; the attempt is logged as `[ADMIN] rechazado`); the only exception is "there is no admin configured at all", where it says which variable is missing. The id comes from the gateway message, not from anything the user types. **(2) text only, on purpose**: no slash version and no `[Summary]`, so it appears in no command list and nobody else can see it; blocked mid-fight like every command that is not in the allow-list. **(3) what it gives** (`aa admingive <what> <amount> [@someone]`, no mention = to yourself; amounts accept `1.500`, `10k`, `1m` through `AmountParser`, "all" is refused): `gold` (`oro`), `dust` (`polvo`), `xp` (`exp`, through `IProgressionRepository.AddXpAsync`, so it can level up) and `item <name…> [quantity]` (any catalog item by name, accent- and case-insensitive; an unknown name answers "¿quisiste decir…?" with up to 8 catalog names that contain what was typed). Boxes, materials, food, eggs, pet food and dragon food go to the BAG; a **weapon or amulet is PUT ON** (replaces the worn piece and starts without enchant, like forging it) and a **tool is PUT ON** in its slot (axe/pickaxe, replacing the old one even if it is worse: it is for testing); for those the quantity does not count. Limits per command: gold and Polvo up to `int.MaxValue`, XP 100 M, 100,000 units of an item; the repository CLAMPS the total at `int.MaxValue` in SQL (`LEAST(old::bigint + n, 2147483647)`) instead of failing with "integer out of range". **(4) it never creates accounts** (a target without `/start` gets a message and nothing) and each give is ONE statement or ONE transaction that locks the user row (10 simultaneous gives sum exactly). **(5) audit trail**: a `[ADMIN] actor -> target: what` line in the server log and an `admin_give` event in `game_events` (`amount` = quantity, `detail` = what and who gave it), which is what to read to check a giveaway; the reply mentions only users (`AllowedMentions(Users)`, never `@everyone` or roles) so the winner of a giveaway gets pinged. To enable it locally put `Admin__UserIds=<id>` in `.env`; in Railway add the same variable (Raw Editor) and restart. **Not built**: several winners in one command, a slash version, giving a dragon or setting a level (the owner can buy a dragon with the gold and level with the XP).
