# UI de Discord: embeds, emojis, íconos, NPCs, ayuda, idioma, /config, banner, /cd

> Texto movido literal desde el CLAUDE.md viejo el 2026-11-12 (en inglés, como estaba). El índice está en CLAUDE.md.

**Readable embeds** (the owner's rule: spaced out, not crowded — use blank lines and columns, not walls of text): `/inventory` is in **TWO COLUMNS** since v0.9.3 (the owner: "madera, minerales, drops, consumibles; los consumibles en una columna sola debajo de minerales"): left = 🪵 Madera and, below, 🩸 Drops de monstruo (`items.type = 'Material'`); right = ⛏️ Mineral and, below, 🍖 **Consumibles** (the owner insisted on that word, not "Comida"; `/shop` and the tavern still say Comida) with the 📦 Cajas stacked under it when both fit in one field.
**One item per line, always.** Discord lays inline fields out three per row, each one third of the width, so a pair would leave the next field climbing into the same row: every row therefore carries a THIRD, EMPTY inline field (zero-width name and value) that closes it — beside real content it adds no height (the huge gaps of v0.9.1 were empty NON-inline fields stacked in their own row; never do that).
A list longer than one field (~15 drops at ~75 chars a line) is split into EVEN parts (8 and 7 lines, `GameModule.PackLines`) with an invisible title on the continuation (never "(1/2)"), and **since v0.26.3 the parts go SIDE BY SIDE, in the same row, before the next block** (rows: Madera | Mineral, Drops | rest of the drops, Consumibles): phones stack the inline fields in the order they are sent, and the old row-by-row grid put the second half of the drops AFTER the Consumibles, like a separate table (the owner's screenshot, 2026-10-26: "Fragmento de Alma" alone at the bottom). The inventory is built from four blocks (wood, minerals, drops, food+boxes); two one-field blocks sit side by side as always, and a block that overflows takes its fields in pairs. If only one of the two columns has anything, it goes full width. **History, so nobody repeats it**: v0.8.3 had three narrow columns, and names like "Cuero Curtido de Pradera" wrapped into two lines (the owner's screenshot); the v0.8.4 "chips" (`icon **Name**: 3` with no-break spaces, U+00A0, several per line) did not hold either because Discord
still breaks a line between the custom emoji (an image) and the text after it, so an item's icon ended up at the END of the previous line, next to the wrong item (the owner's screenshot, v0.9.0) — **never use chips**; v0.9.0–v0.9.2 had the drops one per line at full width, which never broke. The two columns are still a third of the width each, so a long name wraps inside its column (an accepted trade-off the owner asked for; the way back is the v0.9.2 layout, `git show v0.9.2:Modules/GameModule.cs`). Lines are `icon **Name**: 1.234` (bold name, thousands separator; no rarity text — the item emoji, or a coloured dot, carries it, `GameModule.AddFields/PackLines`). A field holds 1024
chars and one emoji code is ~45, so the whole catalog at 9999 of each is ~3900 total, under the 6000 embed limit; only what the player has appears. Emojis inside text are always drawn at 22 px — Discord cannot enlarge them — so bigger icons would need a generated image (not done);
**`/profile` is stacked, one field under the other** (v0.9.1, the owner's request after seeing the bank and Polvo crammed into narrow columns): Experiencia, Vida, ⚔️ Ataque (the number, the weapon's name and, if enchanted, "✨ Filo X (+N %)"), 🛡️ Defensa (same with the amulet), 💰 Oro, 🏦 Banco (only with an account),
✨ Polvo (only if > 0), 🎁 Racha and ✨ Habilidad — ALL non-inline. **Since v0.14.3 the profile no longer lists the pets, the Fuego Nuevo percentages, the blessings or the professions** (the owner, 2026-10-07: "dejalas aparte"): each has its own command — `/pet` (`aa pet|pets`), `/fuegonuevo` (`aa fn`, which now shows "what it gives you today" also when you can renew, and "your blessings"), `/blessings`, `/professions` — and the profile keeps the numbers that fight (attack and defense with their 🔥/🐾 extras), "FN N" in the title and the cosmetic Brasa de Color title/color. **Never use an empty field (`AddField(Blank, Blank)`) as a spacer, and no inline pairs of short fields**: v0.9.1 had both and the owner's screenshot showed a huge gap for every empty field (a name row + a value row + margins) and Polvo/Racha far apart (inline fields sit in a 3-column grid), so v0.9.2 removed them
(Discord already separates stacked fields; the same applies to the inventory, `/enchant` and `/dismantle`). **The weapon/amulet lines carry NO "(+N)" of the piece** (the owner found it useless: it is already inside the big number). The zone is not a field any more: it is the embed's description, one line, "Zona 1: Praderas del Mate (máx. Zona 4)", where the max is the highest UNLOCKED zone by the `/zona` rule
(`ZoneRanking.MaxUnlockedRank`). `/enchant` and `/dismantle` follow the same idea (paragraphs separated by blank lines inside the description, stacked fields). `/cd` has a pets line since v0.18.4 (`CooldownModule.PetLine`, pure: "¡Listo! — N pueden comer" or the time left for the FIRST pet that can still level up, with the player's own Buen Pienso wait; no line without pets, with all at max level, or if reading them fails; before the Daily line; the slash description is 97 characters on purpose — adding "mascotas" to the old one reached 103 and Discord's limit is 100, which would break the registration of EVERY command) and ends with an Arena line (`CooldownModule.ArenaLine`: "anotado ✅ — se juega en 1h 35m" or "¡todavía no te anotaste! ⚠️ ... /arena join"; it reads the real `IArenaService.ListAsync`, which only reads; if the lookup fails the line is simply omitted).
`/shop view` is two inline columns (Comida | Cajas), each item with ITS OWN emoji and a one-line detail, no rarity text and no decorative emojis; the recipe book (`/forge` button, `aa forge recipes [zone]`) is ONE LINE per recipe grouped by zone (v0.27.0; before it was one field per recipe with have/need ✅/❌ per ingredient) and
`/drops` sends one embed per zone (a field per fight type, two short lines per monster). Both were single walls of text
before. Every embed built from a growing catalog must stay under Discord's 6000-character total (all embeds of a message
count together).

**NPC dialogue and the blacksmith scene** — everything a character says lives in ONE pure place, `GameData/NpcDialogue.cs`: tables of lines per
situation for the blacksmith, the shopkeeper, the innkeeper (`/heal`) and ALL 20 monsters (since v0.8.3: intro / when it falls / when it beats you, 15 hunt+travel monsters in `MonsterLines` and the 5 zone bosses in `BossLines`,
keyed by the monster name in the DB; one without its own lines gets generic ones, so adding a monster never leaves it mute). `NpcDialogue.Monster(name, emoji, line, isBoss)` is the one entry point and `AdventureModule.MonsterSays(state, line)` the
shortcut every combat message uses: `/hunt`, `/travel`, `/boss`, `/use` mid-fight and `/autohunt` all show the monster's line on appearing (hunt/travel/boss), on winning and on losing. A line is picked
at random from its table (inject a `Random` to test), always formatted `emoji **Name:** «line»`. To add dialogue, add lines to a table;
a new character is an enum + a table. Every table must keep ≥2 distinct lines (a test checks it). `/forge` (`aa herrero`; the slash `/forge` has NO subcommands — `/forge make|recipes` were removed, `ForgeModule` is now only static logic, while `aa forge make|recipes` still exist for text users and parse unambiguously next to the `aa forge` alias),
`Modules/BlacksmithModule.cs`) is a scene: the blacksmith greets (with his picture if `Images__Blacksmith` is set in the `.env` to a public
image URL — the bot hosts no files — otherwise text only; see "NPC images ship with the bot" below) and a select menu lists the player's zone recipes (✅ craftable / ❌ what's
missing, the same `ForgeChoices` the `/forge make` autocomplete uses); picking one runs EXACTLY `ForgeModule.ExecuteMakeAsync`, so
validations, the atomic charge and the craft event are shared, and the menu is rebuilt after each order. the blacksmith's answer goes in a SEPARATE message right below (`BlacksmithModule.BuildAnswerEmbed`, same as the tavern's) so it doesn't get lost, and the scene is rebuilt after each order. A button ("📜 Ver todas las recetas", `blacksmith_book:{owner}`; since v0.27.0 it replaced the zone select menu `blacksmith_zone`) switches the scene to the whole recipe book (`ForgeModule.RenderRecipesEmbed`, see "Forge recipes") and "↩ Volver a la herrería" (`blacksmith_home:{owner}`) goes back to the greeting; it is view-only — the forge menu still lists the player's own zone. `aa forge recipes [zone]` is the
text equivalent (no argument = every zone). Each menu's custom id carries the owner id so nobody else can use your conversation. Boss victory text depends on
whether it was the FIRST clear of that zone's boss (`highest_zone_cleared` is read *before* applying the victory): the first time it
announces the next zone opens; every later kill says "¡Volviste a ganarle!" and never claims an advance.

**Level-up banner (`GameData/LevelUpCard.cs`, `Services/ProgressNotifier.cs`)** — leveling up used to be one small field ("Ahora sos nivel 7") inside victory/daily/receipt embeds that
already had gold, XP, HP, summary, drop... and got lost. Now it is its own **public gold embed** ("🎉 ¡SUBISTE DE NIVEL! 🎉": mention, `Nivel 6 ➜ Nivel 7`, three columns with max HP +15, ATQ +2 and DEF +1 per level (the ATQ/DEF come from the difference of `CombatStats.BaseAttack/BaseDefense` between the new and the old level, so they follow the formula the combat and `/profile` use; weapon and amulet add separately), "curada al
máximo" full width underneath, a "zona nueva a tu alcance" line when the new level crosses a zone's `min_level`, and a random cheer in the footer). It comes out of the ONE place every XP source already
goes through: they all record a `level_up` event (`GameEventExtensions.RecordVictoryAsync`, the mission/achievement claims), `ProgressNotifier` turns it into a `GameNotice` carrying the
embed, and `NoticeDelivery` delivers it as soon as the command ends (follow-up for slash and button interactions, channel message for text commands; known limit: in a raid only the player who lands the last blow has an interaction to answer, so the other participants still get their banner on their next command, within its 2 minutes). So a new XP source gets the banner for free
as long as it records `level_up`; the in-embed field was removed everywhere (a raid keeps its short per-player line in the shared victory embed, because only the player who landed
the last blow is still "in" an interaction). `GameNotice.ExpiresUtc` (2 min for this one) drops notices that were never delivered, so another raid participant doesn't get a stale
banner hours later glued to an unrelated command.

**The tavern (`/taberna`, `aa taberna`, `Modules/TabernaModule.cs`)** — the shopkeeper IS the innkeeper ("El Tabernero", one character; there is no "Tendero" any more): a scene with his photo, the
price list (two inline columns Comida | Cajas, `ShopModule.BuildViewEmbed`) and four select menus, one per row — eat something from your bag, buy food, buy a box, sell something.
Every pick is ONE unit and runs exactly the existing logic (`ShopModule.ExecuteBuyAsync/ExecuteSellAsync`, `UseModule.ExecuteUseAsync`: same validations, atomic charge, box cooldown and
game events), then the scene is rebuilt with your fresh gold and the innkeeper's answer goes in a SEPARATE message right below (`TabernaModule.BuildAnswerEmbed`: replacing the scene text made it get lost between the price list and the menus). Each menu's custom id carries the owner id. `/shop` (view/buy/sell/sellall) remains as the direct
shortcut for quantities and for text commands; `/shop view` carries no photo on purpose (an `attachment://` thumbnail without its file would make Discord reject the message).

**The inventory opens by TABS (v0.35.0; `GameModule.BuildInventoryViewAsync` / `BuildInventoryView`, select menu `inv_tab:{viewer}:{owner}`, harness `v0350test`; NO migration)** — the owner (2026-10-28): "son demasiados ítems para un inventario" (47 kinds of bag item and growing: fish and cooking were being designed) and, when I offered tabs, "me parece perfecto". `/inventory` and `aa inventory` now open ONE category and a dropdown switches: **🪵⛏️ Recolección** (wood + minerals, two columns), **🩸 Drops de monstruo**, **🍖 Consumibles** (food, pet food and dragon food), **📦 Cajas y huevos**, and **📋 Todo**, which is the complete two-column screen of before (`BuildFullInventoryEmbed`, still what `BuildInventoryEmbedAsync` returns, so the harnesses that read the inventory did not change). The description is a one-line summary of UNITS per category with the open tab in bold (`**🪵⛏️ 10** · 🩸 11 · 🍖 7 · 📦 2`), so you see what you hold without opening anything. **The field titles carry no emoji** ("Madera", "Mineral", "Drops de monstruo", "Consumibles", "Cajas y huevos": the owner, 2026-10-28, because that summary line already shows them and every item has its own icon). The default tab is the first category with something; a requested tab that does not exist or is empty falls back to it; with nothing, or with a single category, there is no dropdown (the usual "no tenés ningún material" notice / nowhere to go). Rows with quantity 0 count as nothing. Only the player who opened the message can use the dropdown (the id carries the viewer and the owner, so looking at someone else's inventory also works by tabs); the owner's name for the new title comes from the guild cache and, if it is missing, the message keeps the title it already had. The option emojis are plain unicode on purpose (a rejected custom emoji would break the whole message). A tab is smaller than the old screen, so the embed limits stop being a risk (the harness checks 100+ lines per tab). **A new bag item type goes in `BelongsToTab` and `InventoryCategories`** (and in `BuildFullInventoryEmbed`, which still lists the types it knows), or it will show in no tab.
